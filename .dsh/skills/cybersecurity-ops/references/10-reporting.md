# 安全报告与发现写作

> 报告的唯一标准：**读者能据此做决定**。管理层要知道“多严重、先做什么、要谁负责”；工程师要知道“怎么复现、怎么修、怎么验证”。不要把扫描器导出粘进 Word 就交差。

## 1. 先确定读者与决策

| 读者 | 关心 | 写法 |
|---|---|---|
| 管理层/业务 owner | 影响、优先级、成本、期限 | 一页摘要、风险语言、明确 ask |
| 工程/运维 | 复现、根因、修复、验证 | 技术细节、命令、代码/配置 |
| SOC/检测 | 日志、规则、误报边界 | 可观测字段、查询、ATT&CK |
| 合规/法务 | 范围、证据、数据、义务 | 事实、时间线、保留链 |
| 客户/监管 | 影响、已采取措施、时间线 | 经批准的口径，不推测 |

同一份报告可以有执行摘要 + 技术附录；不要用同一套语言对所有读者。

## 2. 默认结构

```markdown
# <对象> 安全评估报告
日期/版本/作者/分类

## 1. 执行摘要
- 3–5 条结论（最高风险、影响、置信度）
- 总体风险评级与依据
- 最重要的 3 个行动 + owner/期限
- 范围/限制一句话

## 2. 范围与方法
- 授权方/授权文件/时间窗
- 资产/排除项
- 测试类型（被动/主动/代码/配置）
- 工具/版本/限制

## 3. 发现总表
| ID | 标题 | 资产 | 状态 | Severity | Priority | 证据 | 修复 | 期限 |

## 4. 详细发现
每个 finding 用统一模板（见下）

## 5. 事件时间线（如适用）
UTC + 来源 + 证据 ID

## 6. 修复与复测计划
短期缓解 / 长期根治 / 验证方法 / owner

## 7. 附录
- 证据索引
- 工具输出（脱敏）
- 术语/评分口径
- 版本/变更记录
```

## 3. Finding 模板

```markdown
### V-001 普通用户可读取其他租户发票 PDF

- **状态**：confirmed（已复现，未扩大利用）
- **Severity**：Medium — CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N (6.5)
- **Priority**：P2 — 示例公式约 38 分（P3）；因跨租户 PII 的业务影响，按组织口径上调至 P2，并在附录记录这个例外
- **资产**：https://staging.example.com/api/v1/invoices/{id}
- **影响**：任意登录用户可枚举并读取其他租户发票，含地址、金额、邮箱。
- **前提**：需要普通账号；发票 ID 为顺序整数；无额外 MFA。
- **证据**：E-021 请求/响应；E-022 两个租户测试数据；E-023 对照 403。
- **复现**：
  1. 用 tenant A 的测试账号登录，获取 token（不写入报告）。
  2. `GET /api/v1/invoices/INV-B-1001`，返回 200 与 tenant B 的 PDF。
  3. 换成 tenant B token 请求同一 ID，返回 200；匿名返回 401。
- **根因**：查询按 `invoice_id` 直接取数，未附加 `tenant_id = current_tenant`。
- **修复**：在 repository 层强制 tenant 过滤；增加授权单测；对历史 ID 做审计。
- **短期缓解**：WAF 规则限制导出频率（不能替代修复）。
- **检测**：同一用户短时间访问多个 tenant 的发票 ID；401/403 比例异常。
- **复测**：修复后 tenant A 请求返回 404/403；tenant B 正常；回归测试通过。
- **参考**：CWE-639、OWASP API1:2023。
```

要求：

- 标题写“谁 + 能做什么 + 影响”，不写“SQL 注入漏洞”这种只有类型。
- 状态、severity、priority 分开；每个都有依据。
- 影响写“能/不能”，不夸大；注明前提。
- 证据可定位（文件/包号/日志字段/代码行）。
- 修复具体；短期缓解不能冒充根治。
- 复测可执行。

## 4. 严重性与优先级写法

- **Severity**：CVSS 向量 + 分数；没有向量时写定性等级和依据。
- **Priority**：引用组织 SLA/公式；本 skill 的示例公式见 `03-vuln-triage.md`。
- 不要把“P0”与“Critical”混用；解释两者关系。
- 对未知输入（EPSS/KEV/暴露）明确写 `unknown`，不要默认有利。

## 5. 执行摘要写法

差的摘要：

> 本次扫描发现 312 个漏洞，其中 45 个高危，建议尽快修复。

好的摘要：

> 在 42 个外部资产中发现 3 个可导致客户数据泄露的问题：一个未授权 API 可读取其他租户发票（已复现），一个旧版 VPN 设备存在 KEV 在野利用漏洞（互联网可达），一个 S3 桶可匿名列出（含 12 个测试文件）。建议 24 小时内限制 API/关闭桶/升级 VPN；其余 9 个高危需在 7 天内排期。我们未测试生产支付流程和第三方 SaaS 底层。

要点：

- 用业务语言说影响，不堆 CVE。
- 明确“已确认/疑似”。
- 给出可执行的 3 个动作和期限。
- 说明没测什么，避免“保证安全”的误解。

## 6. 证据与脱敏

- 证据编号贯穿报告；原始证据单独存放。
- 请求/响应保留方法、路径、状态、关键 header；token/Cookie 用 `[REDACTED]`。
- 截图打码：邮箱、手机号、姓名、卡号、内部 IP、客户名。
- 文件/PCAP/内存镜像计算 SHA-256；报告只写哈希和位置。
- 共享前运行：

```bash
python scripts/secops.py redact report.md --pii
```

并人工复核；自动脱敏不能保证覆盖所有敏感信息。

## 7. 修复建议

每条建议包含：

- **做什么**：版本/配置/代码/架构。
- **谁做**：团队/owner（如已知）。
- **多久**：SLA/期限。
- **怎么验证**：复测命令/测试用例。
- **风险**：变更影响/回滚。

避免：

- “加强安全意识”“定期扫描”“使用最佳实践”这类不可执行建议。
- 只写“升级”但不给修复版本/兼容性。
- 把 WAF 规则当永久修复。
- 不区分缓解与根治。

## 8. 机器可读输出

- **SARIF 2.1.0**：适合代码扫描/CI；包含 ruleId、level、location、message。
- **JSON**：保留状态、severity、priority、evidence、remediation 字段。
- **CSV**：给漏洞管理/工单导入；字段稳定。
- CSV 不可信文本可能被表格软件当公式。CLI 对可疑前缀加单引号；编辑/另存/重新导入可能丢失保护，按纯文本导入，机器交换优先 JSON。Markdown 中的证据应转义 HTML、链接和代码围栏，不直接渲染来自目标的标记。
- 同一发现不要在多套格式里用不同 ID；以规范 ID 为主键。

示例 JSON：

```json
{
  "id": "V-001",
  "title": "普通用户可读取其他租户发票 PDF",
  "asset": "https://staging.example.com/api/v1/invoices/{id}",
  "status": "confirmed",
  "severity": "medium",
  "cvss": {"version": "3.1", "vector": "CVSS:3.1/AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N", "score": 6.5},
  "priority": "P2",
  "cwe": ["CWE-639"],
  "evidence": ["E-021", "E-022", "E-023"],
  "remediation": "在 repository 层强制 tenant_id 过滤，并增加跨租户回归测试",
  "retest": "tenant A 请求 tenant B 发票返回 404/403"
}
```

## 9. 质量检查

- [ ] 执行摘要能在 1 分钟内读懂；有明确 ask。
- [ ] 每个 finding 有状态、severity、priority、证据、影响、修复、复测。
- [ ] `confirmed` 有直接证据或受控复现；`suspected` 没写成确定。
- [ ] 没有扫描器原始堆砌；重复已合并。
- [ ] 时间统一 UTC；证据可定位。
- [ ] 已脱敏；无真实凭据/客户数据。
- [ ] 限制/未测范围写清。
- [ ] 术语/评分口径一致；没有自相矛盾。
- [ ] 版本/日期/作者/分类齐全。
- [ ] 对外版本经过授权批准。

## 10. 常见坑

- 把 CVSS 分数当唯一结论，忽略业务影响。
- 用“高危”描述一切；没有优先级。
- 报告只有问题，没有证据/复现，工程无法修。
- 修复建议不可执行，或把缓解当根治。
- 同一漏洞在多个章节重复，编号不一致。
- 执行摘要与技术细节矛盾（摘要说“无数据泄露”，详情说“可读 PII”）。
- 脱敏不彻底：URL 参数、日志、截图、附件元数据。
- 没有复测/关闭标准，漏洞永远“待修复”。
